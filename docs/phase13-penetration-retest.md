Specification gate: Phase 13 — Security, reliability, and performance hardening

## What this is

The Phase 0 review closed on the claim that a sufficient control existed _in the design_ for every critical and high threat. This retest asks the different question Phase 13 owes: does the control exist in the code, and does it hold when somebody attacks it on purpose?

The method is adversarial tests written from the attacker's side of each boundary, kept separate from the unit tests that prove each module's intended behaviour. A control is only counted as retested when a test tries to break it and fails to.

## Method and limits

| Aspect              | This retest                                                                                                                          |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Technique           | Automated adversarial suites plus a manual review of every outbound call site and every untrusted-input parse                        |
| Boundaries in scope | TB-A through TB-G, excluding native iOS runtime behaviour                                                                            |
| Not in scope        | Physical-device Sign in with Apple, live Apple Sandbox commerce, deployed Railway network posture, and third-party platform controls |
| Evidence            | `npm run test --workspace @fortuneness/api` and `npm run test:db --workspace @fortuneness/api`                                       |
| Environment         | Windows workstation, local PostgreSQL for the integration suites, no network calls to Apple                                          |

This is not a substitute for an external assessment of the deployed service. It is the strongest evidence obtainable before Railway staging exists. The rows marked _external gate_ below say plainly what is still unproven.

## Transport and boundary hardening confirmed by this retest

- The server does not advertise its implementation, and `nosniff` is set.
- An attacker-chosen `X-Request-ID` that is not a UUID is replaced, so it cannot be reflected into a log or a response.
- A cross-origin request from an unconfigured origin is refused without an allow-origin header.
- A JSON body smuggled under `text/plain` is not parsed.
- `__proto__` and `constructor` keys in a request body do not mutate `Object.prototype`.
- An ordinary request body is bounded far below the commerce bound; only the two Apple routes carry the larger bound.
